# Activity Feed is a community feed on the home page, not a per-user feed

The comments spec originally described a per-user "activity feed" on a profile/dashboard page, served by `getUserComments(userId)`. Grilling the plan surfaced a contradiction: the feed's material (comments) lives on spots, users land on `/` first, and a public home page is more social. We decided to show a **community-wide recent-comments feed on `/`** (read-only, newest first, each item linking to its spot), and to **drop the per-user feed entirely** — there is no `getUserComments`, `useUserComments`, or dashboard/profile feed. Each comment still appears embedded in its owning spot detail page.

The alternative (per-user feed on a public profile page, as originally specced) was rejected because the feed's natural unit is the comment-on-a-spot shared with everyone, and the home page is where both anonymous visitors and logged-in users land — a per-user feed serves only the author and duplicates what they already see on spot pages. Consequences for implementers: mutations invalidate the `["recent-comments"]` feed key as well as `["comments", spotId]`, and the backend comment controller must populate `spot` (and `author.avatar`) in its fixed `POPULATE`, since client `populate` params are overridden.
